## 6. 房型和商品映射进度

### PMS 多房型归一

房型映射现在支持一个统一 `room_type_id` 对应多个 PMS 原始房型名称，用于解决“PMS 两个房型对应 OTA 一个房型”的实际场景。

当前规则：

- 多个 PMS 房型名称可以共享同一个统一 `room_type_id`。
- 同一个 PMS 原始房型名称不能同时属于两个不同统一房型 ID。
- 房型映射页面按 PMS 原始房型逐行展示；同一统一房型可出现多行，每行可单独停用。
- 行内停用只关闭当前 `pms_byh` 别名的精确匹配，不影响同一统一房型的其他 PMS 别名或 OTA 商品关系。
- 每个 PMS 别名单独保存为 `pms_byh` 基础映射记录；数据库现有唯一键已经支持这种多别名结构，不需要新增 Schema。
- 使用“新增”方式再次保存同一个统一房型 ID 时，会合并已有 PMS 别名，不再把旧 PMS 房型覆盖掉。
- 使用“编辑”方式可以明确移除某个 PMS 别名；被移除的别名不再参与后续匹配。
- PMS 业务表仍按原始房型名称精确匹配，因此不同 PMS 名称可以最终写入同一个统一 `room_type_id`。
- OTA 商品匹配、美团钟点房判断保持原有独立逻辑。

对应修复：PR #12 `fix: 统一房型支持多个 PMS 房型别名`。

## 7. PMS 近期关键稳定性修复

### 7.1 凌晨 FORECAST / ROOM_STATUS 查询窗口

已经确认 PMS 预测服务在凌晨使用当前小时可能返回业务错误，而查询当日 12:00 可以正常工作。

当前规则：

```text

06:00–23:59 -> beginHour = 当前整点
```

FORECAST 和 ROOM_STATUS 共用该窗口。

### 7.2 PMS 网络抖动保护

曾实际出现同一 PMS 主机多个端口的连接层异常：

- Web 报表页面：`ERR_CONNECTION_CLOSED`
- API：`SSL UNEXPECTED_EOF_WHILE_READING`

这类故障没有明确 403/429，因此不要直接认定为平台限流或登录失效。

当前 `fetch_main.py` 已加入：

- 各报表之间随机 2–5 秒等待。
- 连续 3 个报表失败后进行轻量网络探测。
- 探测失败或 5xx 时停止本轮剩余访问。
- 剩余任务标记为未采集，后续 ETL 自动跳过。

### 7.3 JD01 空结果

JD01 返回 0 条预订是合法结果。

此前 ETL 会在：

```python
print(data_list[0])
```

处触发 `IndexError`，导致整个 PMS ETL 中断。

PR #9 已修复：


现在空结果只输出提示，正常执行 0 条写入并继续处理后续 PMS ETL。

### 7.4 后台采集状态自动收尾

面板启动的整批采集会记录后台 `runner.py` 进程 PID。状态页读取时如果发现任务仍显示
“正在启动/运行/中断”，但对应进程已经退出，则自动将本轮及尚未执行的任务收尾：

- 已请求停止的任务标记为“已中断”。
- 未请求停止但进程异常退出的任务标记为“失败”，并说明未返回完成状态。

这样服务重启、子进程异常退出或中断后，不会长期把 PMS 等待执行任务显示为“进行中”。

面板只会对明确记录了后台 `runner.py` PID 的直接启动任务进行“进程已退出”自动收尾；
定时调度器直接运行的批次不带该 PID，必须保留实际的运行状态，避免页面将未执行任务误标为
0 秒失败并隐藏“中断当前采集”按钮。

携程商品采集完成后会将最新商品 ID、商品名、`product_cipher`、可调价标识和钟点房标识同步到
`hotel_room_type_mapping`；基础房型记录仍不保存商品级字段。

## 8. 美团页面型任务当前策略

美团部分数据并非稳定的纯 API 调用，而是依赖登录后的页面加载、iframe、动态请求和 Edge profile。

当前三个高风险/页面型任务主动降低访问频率：

| 任务 | 随机冷却 |
|---|---:|
| 促销开通状态 | 10–14 小时 |
| 视频上传状态 | 22–26 小时 |
| 近 30 天推广效果 | 22–26 小时 |

当前冷却已经改为“实际结果后进入冷却”：

```text
冷却期调用 -> 跳过，不刷新时间
真正开始采集 -> 只记录 last_attempt_at
成功写库 -> success 冷却
实际失败 -> failure 冷却
```

对应重要合并提交：

```text
2e6a6eea57bb1d32a3737c1f5f274b77a72c9879
fix: 美团页面任务仅在实际结果后进入冷却
```

### 美团视频统计跨域会话（2026-10-10）

视频管理页的统计请求实际位于 `tdc.meituan.com`，该域需要当前账号的 EB 会话。视频任务现在将配置中的 `eb_cookie` 同步到 `eb.meituan.com` 和 `tdc.meituan.com`，将 `me_cookie` 同步到主站；缺少任一 Cookie 时提前报错，避免使用旧账号的资料目录会话。接口返回 303 时明确提示视频接口未登录，不再仅输出“response is invalid”。实测同一新账号仅补主站 Cookie 或仅补 EB 主站域均返回 303，补齐 TDC 域后返回成功并取得三类视频统计。现有快照写入、浏览器锁及 22–26 小时冷却规则保持不变。

### 推广效果页面注意

推广效果脚本仍使用页面产生的 `/paginateQueryPlanAndLaunch` 动态请求，页面等待时间当前是 12 秒。

该页面曾在人工点击“推广通”时也进入美团风险控制。因此当前方向是降低触发频率，而不是增加刷新/重试或尝试绕过平台控制。

### 预约发票状态

预约发票当前页面会直接显示“当前门店暂未开通，快去开通预约发票吧！”。状态采集优先识别该页面空态并写入 `CLOSED`，旧的“酒店发票信息维护”链接仅保留为兼容后备。

### 公益流量与酒店亮点导航

工作台会先从 `eb.meituan.com` 跳转到 `me.meituan.com` 包装页，再异步加载菜单。公益流量必须先展开“促销推广”，酒店亮点必须先展开“信息管理”；采集器等待包装页完成跳转，从同名节点中选择可见菜单，再等待父菜单和子菜单出现后正常点击，避免导航中断、隐藏副本或固定短等待导致定位超时。

## 9. 浏览器与动态签名现状

当前美团部分采集依赖页面自己产生的动态签名请求，而不是保存一条长期不变的签名 URL。

已经存在公共浏览器 profile 锁，用于减少：

- 定时任务之间争抢 Edge profile。
- 人工登录/操作与自动采集同时占用 profile。

修改页面型采集代码前，应先确认是否依赖这套动态请求捕获和浏览器锁。

## 11. 已经确认、不需要重复争论的设计

为了避免新 Codex 会话重复排查已经确认的问题：

- 每个数据库只对应一家酒店，不需要优先考虑跨酒店同库隔离。
- 一个统一 `room_type_id` 允许对应多个 PMS 原始房型名称；不要把这种多对一关系自动判定为冲突。
- 同一个 PMS 原始房型不能同时映射到两个不同统一房型 ID。
- `ctrip_order_loss_monthly` 当前快照/排名语义是有意设计。
- 评价回复调度读取 `price_scheduler.interval_minutes` 是当前有意设计。
- 登录/账号切换自动识别酒店参数失败时保留旧参数并告警是有意设计。
- 美团商品 `is_hour_room` 和统一房型映射 `is_hour_room` 保持独立判断。
- PMS 00:00–05:59 查询当日 12:00 是经过实际运行确认的规则。
- ROOM_STATUS 的查询 `beginHour` 与真实 `snapshot_hour` 不一致并不代表数据错误。
- 美团页面型任务主动降低频率是为了降低访问压力和风险控制触发概率。
